# Audit ConX — 2026-07-07

> Audit approfondi multi-dimensions (backend, sécurité, frontend, data/infra, tests & docs), mené sur la stack en fonctionnement (3 122 513 bâtiments en base, backend `0.13.0-j13`, frontend `0.14.0-j14`). Chaque constat a été vérifié dans le code réel. Findings recoupés par plusieurs agents = fiabilité renforcée (signalés ⨯N).

## Verdict global

Le projet est **bien plus solide que ce que sa doc de pilotage laisse croire** : architecture en couches saine, SQL 100 % paramétré, RLS correcte, aucun secret jamais committé (41 commits scannés), index DB complets et effectivement utilisés (EXPLAIN à l'appui), scoring/carbone/ML testés, docs techniques (`SCORING`, `CARBON`, `ML_DPE`, `API`) fidèles au code.

Mais il y a **des trous sérieux concentrés sur 3 axes** :
1. **Sécurité de la config démo** : le combo `CONX_DEV_BYPASS_AUTH=1` + tunnel ngrok rend aujourd'hui possible, pour un inconnu disposant de l'URL, l'exfiltration de la clé Anthropic et du `service_role` Supabase. C'est le point le plus grave.
2. **Robustesse runtime** : appels bloquants (IfcOpenShell, WeasyPrint, Anthropic, supabase-py) sur l'event loop async mono-worker → risque de **gel visible pendant la démo**.
3. **Fiabilité du projet** : CI qui n'a jamais tourné, suite de tests non verte dans son propre conteneur, ré-ingestion qui casse silencieusement la carte, et doc de pilotage (`CLAUDE.md`) figée au 23 mai qui prétend encore « pré-implémentation ».

**Décompte** : 6 CRITIQUES · 13 MAJEURS · ~25 MINEURS · findings INFO/hygiène.

## 🔴 CRITIQUES (à traiter avant toute nouvelle exposition publique)

### C1 — Exfiltration des secrets via l'export PDF (LFI/SSRF WeasyPrint) ⨯2
**`routers/agents.py:822-947` → `plan_export.py:72-114,363` → `templates/plan_rapport.html:378`**
`export_plan_pdf` accepte `req.plan_text` **sans validation**, `_markdown_to_html` ne sanitize pas le HTML, le template rend `{{ plan_html|safe }}`, et WeasyPrint 63.1 résout `file:`/`http:` par défaut. Un POST avec `plan_text` contenant `<link rel="attachment" href="file:///app/.env">` fait lire le `.env` (vraies valeurs : `ANTHROPIC_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET`, `INTERNAL_SHARED_TOKEN`) et l'embarque dans le PDF retourné. Conteneur en **root**. Non authentifié en démo (cf. C2). Même moteur non durci dans `ifc/pdf.py`.
**Fix** : `url_fetcher` restreint (refuser `file:` et hôtes externes) + sanitizer HTML (bleach/allowlist, retirer `<link>`/`<object>`) avant `|safe`. Appliquer aux deux générateurs PDF.

### C2 — Bypass d'auth global + service_role via ngrok ⨯2
**`auth.py:121-172` · `supabase_client.py:87-93` · `.env:27` · `.env.example:31`**
Avec `CONX_DEV_BYPASS_AUTH=1` (valeur réelle du `.env`, **et défaut livré dans `.env.example`**), toute requête sans JWT reçoit un user fictif sur `/api/buildings`, `/api/exports/*`, `/api/ifc/*`, `/api/agents/*`. Pire : `supabase_for_user` bascule alors sur `SUPABASE_SERVICE_ROLE_KEY` qui **bypasse la RLS** → lecture/écriture des données de tous les utilisateurs, et l'IDOR sur `/api/ifc/pdf/{id}` (ownership reposant uniquement sur la RLS) se rouvre. Exposé via ngrok = API admin publique.
**Fix** : retirer le bypass du `.env` **et de `.env.example`** ; refuser de démarrer si bypass actif ET `NGROK_PUBLIC_URL`/`ENV=prod` présent ; utiliser un vrai compte Supabase de démo ; ajouter `.eq("user_id", …)` explicite en défense en profondeur.

### C3 — Appels bloquants sur l'event loop async (gel démo)
**`routers/ifc.py:179-199` · `routers/agents.py:442-445,930-957` · pattern supabase-py transversal**
Handlers `async def` qui appellent du CPU/IO synchrone sans `to_thread` : `validate_ifc` (IfcOpenShell, plusieurs s), `render_pdf`/`render_plan_pdf` (WeasyPrint, 1-3 s), `create_session`+`send_user_message` Anthropic (sans `timeout=`, défaut SDK 10 min), et **tous** les appels supabase-py (httpx sync, 100-500 ms chacun). Backend mono-worker → un upload IFC ou un export PDF **gèle le stream SSE du Mode Projet** et toutes les requêtes concurrentes. Le code connaît pourtant `asyncio.to_thread` (utilisé dans `_send_with_replay_fallback`) — application incohérente.
**Fix** : `await asyncio.to_thread(...)` sur tout appel bloquant + `anthropic.Anthropic(timeout=30.0)`.

### C4 — Ré-ingestion BDNB vide les tuiles MVT (carte cassée silencieusement)
**`ingest_bdnb.py:254-300` · `sql/migrations/011:15` + `012:9-37`**
`apply_migrations()` rejoue **toutes** les migrations à chaque run. `011` fait `DROP VIEW … CASCADE` (détruit les matviews), `012` les recrée `WITH NO DATA`. Donc `python scripts/ingest_bdnb.py 59` → `/tiles/buildings_mv` vide → **carte frontend blanche** jusqu'à un `REFRESH` manuel. Or le script `scripts/refresh_tiles_matviews.py` référencé par `012:50` et `docs/TILES_MVT.md` **n'existe pas** (confirmé).
**Fix** : table `public_data.schema_migrations` (n'appliquer que le nouveau) + créer le script de refresh (`CONCURRENTLY`, les unique index existent) + l'appeler en fin de pipeline.

### C5 — Martin expose les vues NON matérialisées : tuiles à 11,7 s (DoS accidentel)
**`martin.yaml:12-13`**
L'auto-publish sert tout le schéma `tiles`, y compris `buildings_v`/`buildings_centroids_v`/`commune_passoires_heatmap_v` (ST_Transform à la volée sur 3,1 M lignes, non indexé). Mesuré live : `GET /buildings_v/14/... → 11,73 s` vs `/buildings_mv/... → 0,019 s`. Le frontend utilise bien `_mv`, mais n'importe quel client (ou régression) peut saturer PostgreSQL.
**Fix** : sortir les vues `_v` du schéma `tiles`, ou lister explicitement les sources publiées.

### C6 — CI fantôme + `CLAUDE.md` mensongère ⨯2
**`.github/workflows/ci.yml:5,7` · `CLAUDE.md:5-7,396`**
Le repo **n'a aucun remote git** → GitHub Actions n'a jamais tourné. De plus le trigger est `branches: [main]` alors que la branche de travail est `master`. La règle « tests avant chaque commit » ne repose que sur la discipline locale. En parallèle, `CLAUDE.md` — auto-proclamée « source de vérité, à lire avant tout » — affiche « **Statut : Pré-implémentation (aucun code applicatif écrit)** » et « Prochain : J5 » alors que le projet est livré jusqu'à J17+, marketplace incluse, avec 2,7 M prédictions ML en base. Toute nouvelle session suivant sa propre consigne est induite en erreur.
**Fix** : pousser vers un repo privé (D-010), aligner le trigger sur `master`, réécrire l'en-tête + §7/§11/§12 de `CLAUDE.md`.

## 🟠 MAJEURS

**Sécurité / backend**
- **M1 — IDOR sur le stream SSE** (`agents.py:532-552`) : `stream_plan` fait `_ = user` et streame n'importe quel `session_id` sans vérif d'appartenance (contrairement à `send_plan_message`). Même trou sur `export_plan_pdf`. → répliquer le lookup RLS `agent_sessions`.
- **M2 — Upload IFC lu entièrement en RAM avant contrôle de taille** ⨯2 (`ifc.py:152-157`) : `await file.read()` matérialise des Go avant le test 200 Mo → OOM trivial, non-auth en démo. → lecture par chunks / `Content-Length`.
- **M3 — Pagination `list_events` plafonnée à 200 events** (`agents_client.py:240-253`) : SSE aveugle au-delà de 200 events (session longue) et re-télécharge tout à chaque poll (O(n) réseau). → itérer le pager ou `created_at_gt`.
- **M4 — Persistance Supabase non rattrapée après coût engagé** (`agents.py:448`, `ifc.py:202`) : un échec d'insert renvoie 500 alors que la session Anthropic est payée / le PDF généré. → try/except best-effort + flag `persisted:false`.
- **M5 — Export `/exports/strategie.*` : tri non borné sans filtre obligatoire** (`exports.py:94-116`) : `ORDER BY score_total` sans `LIMIT` SQL ni filtre requis → tri de 3,1 M lignes, risque timeout 30 s + pool monopolisé. → `LIMIT` SQL + exiger un filtre comme `internal.py`.

**Frontend**
- **M6 — `urlTransform={(url)=>url}` désactive la sanitisation react-markdown** ⨯2 (`PlanChat.tsx:645,690`) : réautorise `javascript:`/`data:` dans les liens des plans IA (contenu LLM alimenté par données externes). Pas de `rehype-raw` donc pas de `<script>` injecté → self-XSS au clic, impact limité mais réel. → allowlist de schemes (`http/https/mailto/marketplace`).
- **M7 — État du chat non réinitialisé au changement de `:id`** (`Projet.tsx:75`, `PlanChat.tsx:147`) : plan/session du bâtiment A collés sur la fiche de B, closures figées sur le premier bâtiment. → `<ProjetView key={id} …>` (corrige aussi le non-recentrage carte M9).
- **M8 — Fallback SSE affiche un message utilisateur FABRIQUÉ** (`PlanChat.tsx:204,318-343`) : après 3 échecs de reco, le cache écrase le texte streamé et code en dur « Et plutôt avec du chanvre ? » pour toute v≥2. En démo jury = mensonge visible. → conserver le vrai `user_message` + badge « plan pré-calculé ».
- **M9 — Race condition autocomplete** (`SearchBar.tsx:28-34`) : pas d'annulation → réponse « lil » écrase « lille » ; exception fetch non attrapée. → `AbortController` + `.catch`.
- **M10 — Troncature silencieuse à 2 000 bâtiments** (`StrategieMap.tsx:117,163`) présentée comme décompte exhaustif alors que la vue peut en contenir 40 000 → carte biaisée. → « 2 000+ (vue partielle) » ou bascule tuiles MVT.

**Data / infra**
- **M11 — Restore BDNB non idempotent de façon fiable** (`ingest_bdnb.py:160-217`) : skip « >0 tables » + `ON_ERROR_STOP=0` → restore partiel skippé définitivement, non reprenable sans DROP manuel. → `ON_ERROR_STOP=1` + marker `.restored.done` sur succès complet.
- **M12 — Pas de versionnage de migrations, 3 stratégies contradictoires** (rejoue-tout / si-absent / manuel Supabase) → drift de schéma garanti. → table `schema_migrations` + `scripts/sql/README.md` (ordre opérationnel complet).
- **M13 — Image Docker avec `--reload` gravé + bind mount rw qui masque l'image** (`Dockerfile:34`, `compose:44`) : le code de l'image (2 GB) ne tourne jamais ; en prod sans mount → uvicorn en reload mono-worker. → CMD prod sans reload + `docker-compose.override.yml` dev.

**Tests / hygiène**
- **M14 — `data/fdes_static.json` non versionné** (`.gitignore:34` `data/` ignoré, D-014 dit « versionnée ») : checkout frais → module carbone cassé + 8 tests FAIL. → `!data/fdes_static.json` + commit.
- **M15 — Aucun test frontend** (package.json sans script test, Playwright J21 jamais fait) et **`routers/buildings.py` (plus gros module métier) sans aucun test**, exports CSV/GeoJSON (montrés en démo) sans test, endpoint SSE sans test d'intégration.

## 🟡 MINEURS (sélection ; liste complète dans les rapports d'agents)

- **Suite de tests non verte dans son conteneur** : 172 PASS / 9 FAIL / 24 SKIP silencieux. Causes : chemins `parents[3]` faux en conteneur (`carbon/incorpore.py`, `test_scoring`), password placeholder `changeme_local_only` dans `DATABASE_URL_LOCAL` → 24 invariants DB skippés, `test_export_pdf_requires_auth` sensible au bypass env.
- **Postgres non tuné** pour 30 GB : `shared_buffers=128MB`, `work_mem=4MB` (tri disque 76 MB observé), `shm_size=64MB` (risque parallel scan PostGIS). → `-c shared_buffers=2GB -c work_mem=32MB` + `shm_size:1g`.
- **`GET /api/buildings` sans filtre = seq scan 3,1 M + 5,2 s/page** (`buildings.py:139`). → exiger bbox/dept comme l'endpoint interne.
- **`vite.config.js` (compilé) shadow `vite.config.ts`** : futures modifs du `.ts` silencieusement ignorées. → supprimer le `.js` + `*.tsbuildinfo`, gitignore.
- **Duplication massive métadonnées Marketplace** (catégories × 4 fichiers, email en dur × 4). → `lib/marketplace.ts`.
- **`Projet.tsx` = 1 485 lignes, 25+ composants** dans un fichier. → découper `components/projet/` + `lib/format.ts`.
- **Injection de formule CSV** (`exports.py:288`) : cellules `=/+/-/@` interprétées par Excel. → préfixe `'`.
- **npm audit** : 2 vulns *moderate* (`react-router-dom` 6.27, open redirect) → `npm audit fix`. **Vite 5.4.9** < 5.4.15 (CVE dev-server, non exposé actuellement) → bump.
- **Injections f-string SQL dans `ingest_bdtopo.py`** (dept CLI non validé) — opérateur local, risque faible mais casse le SQL.
- **`/docs`, `/redoc`, `/openapi.json` publics via ngrok** (+ Swagger « Try it out » exécutable avec le bypass). → `docs_url=None` en démo.
- **Divers correctness** : `_decode_cursor` ne valide pas les types → 500 au lieu de 400 ; `float(dpe_coefficient…)` sans garde None → 500 sur fiche ; contraste DPE A/B < WCAG AA ; badge debug `z=12.3` visible ; drag flicker Ifc ; lien RNB cassé si null.

## ✅ Points sains vérifiés (à préserver)

- **Sécurité** : aucun secret dans l'historique git (41 commits), `.env` gitignoré, JWT HS256 avec `audience`+`exp`+`sub` requis (pas de `alg=none`), `/api/internal/*` en `hmac.compare_digest` fail-closed indépendant du bypass, CORS sans wildcard+credentials, RLS `auth.uid()=user_id` sur les 4 tables `app`.
- **SQL** : 100 % paramétré `$n` ; seules interpolations = noms de schéma via whitelist `_BDNB_DEPTS`.
- **DB** : 45 index sur `public_data`, tous utilisés (EXPLAIN confirmé : GIST centroid, partiels commune/iris, unique DPE pour le `ON CONFLICT`) ; scoring UPSERT réellement idempotent/reprenable ; garde-fous ML sérieux (dry-run, invariants pré/post) ; traçabilité `thresholds_version` (sha256).
- **Archi** : couches propres (routers fins, `scoring/`/`carbon/`/`ml/` purs sans I/O), pagination curseur sans OFFSET correcte, SSE avec circuit-breaker + keepalive + timeout, fallback replay B-001 testé (5 tests).

- **Docs techniques** : `SCORING`/`CARBON`/`ML_DPE`/`API`/`MODE_PROJET`/`IFC` fidèles au code (17 routes vérifiées une à une).
